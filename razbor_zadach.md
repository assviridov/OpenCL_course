## Задача 1. Сложение векторов

### Постановка

Даны два целочисленных вектора A и B длины N. Вычислить поэлементную сумму
C[i] = A[i] + B[i]. Имеется CPU-версия (`VectorSum`) — эталон для проверки.
Требуется GPU-версия (`VectorSumCL`).

### Что нового

Первый контакт с моделью GPU: хост-API, понятие work-item, одномерный NDRange.

### Разбор решения

**1. Декомпозиция — суть всего занятия.**

```c
// CPU: один исполнитель, N итераций
for (int i = 0; i < N; i++)
    C[i] = A[i] + B[i];
```
На GPU исполнителей (work-item'ов) ровно N, и у каждого цикл состоит из
**одной итерации**. Номер своей итерации исполнитель узнает через `get_global_id(0)`.
Паттерн называется **map**: один work-item = один выходной элемент.

**2. Ядро (полностью, 2 строки логики):**

```c
__kernel void sum(__global const int *A,   // вход: массив на устройстве, только чтение
                  __global const int *B,
                  __global       int *C,   // выход: запись разрешена
                  const int N)
{
    int i = get_global_id(0);   // номер элемента = номер исполнителя (0..N-1)
    C[i] = A[i] + B[i];
}
```

Элементы языка, которые здесь появляются:
- `__kernel` — функция, которая будет исполнена параллельно на устройстве;
- `__global const int *A` — указатель на память устройства; `const` — ядро не меняет;
- `get_global_id(0)` — уникальный номер work-item'а по размерности 0;
- тело ядра — это тело цикла из CPU-версии, «развернутое» в параллель.

**3. Хост-код — рецепт из 4 шагов** (все они в `main()` в порядке выполнения):

```cpp
// шаг 1: память на устройстве и загрузка данных
cl_mem bufA = clCreateBuffer(context, CL_MEM_READ_ONLY,  sizeof(int)*N, NULL, &err);
clEnqueueWriteBuffer(queue, bufA, CL_TRUE, 0, sizeof(int)*N, A, 0, NULL, NULL);
// шаг 2: сказать ядру, с чем работать (буферы - по указателю, скаляры - по значению)
clSetKernelArg(kernel, 0, sizeof(cl_mem), &bufA);
clSetKernelArg(kernel, 3, sizeof(int),    &N);
// шаг 3: сколько исполнителей и запуск
size_t global = N;
clEnqueueNDRangeKernel(queue, kernel, 1, NULL, &global, NULL, 0, NULL, &kernelEvent);
clFinish(queue);                    // ждем завершения
// шаг 4: забрать результат
clEnqueueReadBuffer(queue, bufC, CL_TRUE, 0, sizeof(int)*N, C, 0, NULL, NULL);
```

Размер сетки задается третьим аргументом `clEnqueueNDRangeKernel` (число измерений, здесь 1)
и пятым (размеры по измерениям). Вектор — одномерный случай.

**4. Проверка** — вывод GPU-версии должен совпасть с CPU-эталоном посимвольно
(данные одинаковые: `vector.txt`).

**5. Замеры и главный вывод занятия** (Apple M2):

| N | CPU | GPU kernel only | GPU transfer + kernel |
|---|---|---|---|
| 25 | 0.001 мс | 0.14 мкс | 1.3 мс |
| 1 000 000 | 0.72 мс | 4.3 мкс | 2.6 мс |

Ядро быстрее CPU-цикла на ~2 порядка, но полный цикл GPU-версии — медленнее:
доминирует перенос данных, а на 25 элементах — накладные расходы на запуск.
**GPU выгоден при большой вычислительной работе на один байт данных.**

### Типичные ошибки

- передать скаляр (`N`) как `sizeof(cl_mem)` (или  наоборот буфер как `sizeof(int)`) — типы аргументов
  ядра и `clSetKernelArg` должны совпадать;
- забыть `CL_TRUE` в `clEnqueueReadBuffer` (неблокирующее чтение вернется до готовности
  данных);
- забыть `clFinish` (дождаться завершения всех потоков на устройстве) перед чтением;
- размер сетки `global` не равен N — часть элементов не обработана (или выход за границы).

## Задача 2. Сложение матриц

### Постановка

Даны две матрицы A, B размером M×N (M=8 строк, N=5 столбцов — **прямоугольные**).
Вычислить C[i][j] = A[i][j] + B[i][j]. Требуется GPU-версия; CPU-версия — эталон.

### Что нового

Двумерная топология задачи: 2D NDRange и линейная индексация двумерных данных.

### Разбор решения

**1. Индексация row-major — главный элемент задачи.**
Матрица хранится в одномерном массиве «строка за строкой»:

```
            столбцы:   0     1     2   ...  N-1
строка 0:          [ 0     1     2   ...  N-1 ]
строка 1:          [ N    N+1   N+2   ... 2N-1 ]
строка i:          элемент (i, j) -> индекс i * N + j
```

Множитель — **число столбцов N**: чтобы попасть в начало строки i, надо
перешагнуть i полных строк по N элементов.

**2. Декомпозиция.** Сетка M×N work-item'ов: один work-item = один элемент матрицы.
Сравнение с CPU-циклами — оба цикла «исчезли» в сетку:

```c
// CPU: два вложенных цикла
for (int i = 0; i < m; i++)          // строки  -> станет get_global_id(1)
    for (int j = 0; j < n; j++)      // столбцы -> станет get_global_id(0)
        C[i*n+j] = A[i*n+j] + B[i*n+j];
```

**3. Ядро:**

```c
__kernel void sum(__global const int *A,
                  __global const int *B,
                  __global       int *C,
                  const int M,               // строк
                  const int N)               // столбцов
{
    int col = get_global_id(0);              // внутренний цикл CPU-версии
    int row = get_global_id(1);              // внешний цикл CPU-версии
    int i = row * N + col;                   // та же формула, что в CPU-версии
    C[i] = A[i] + B[i];
}
```

**4. Запуск — порядок размерностей:**

```cpp
size_t global[2] = { (size_t)N, (size_t)M };   // {столбцы, строки}
clEnqueueNDRangeKernel(queue, kernel, 2, NULL, global, NULL, 0, NULL, &kernelEvent);
```

Размерность 0 — «быстрая»: номера соседних work-item'ов отличаются на 1. Ее отдаем
столбцам, потому что в памяти соседние элементы строки лежат подряд —
запросы к памяти соседних исполнителей сливаются в блоки (коалесценция).
Правило запоминаем: **размерность 0 — то, что подряд в памяти**.
Контрольный вопрос студентам: что будет, если поменять `{N, M}` на `{M, N}`?
Ответ: у части work-item'ов `row*N+col` укажет на чужой элемент или за границу массива.

**5. Почему матрица прямоугольная (M≠N).** При M=N студенты часто «угадывают»
индексацию; разные M и N заставляют честно ответить, какая размерность за что отвечает.

**6. Проверка** — построчная сверка матрицы C с CPU-эталоном.

### Типичные ошибки

- перепутать местами `{M, N}` в `global` или множитель в `row * N + col`
  (`row * M` — неверный!);
- передать в ядро только N, забыв M (или наоборот) — на этапе компиляции не ловится;
- считать, что `get_global_id(0)` — это строка (в нашей раскладке — столбец).

## Задача 3. Фильтрация биомедицинского сигнала (ДЗ)

### Постановка (упрощенная)
(задача дается в теме 7.1 как домашняя задача Е (https://drive.google.com/file/d/1DIYSqoxix0NiBAeg5-WPRO4PW2_66nW2/view))

Сигнал: N каналов, в каждом M отсчетов. К каждому каналу применяется «фильтр» —
набор из K коэффициентов b (K нечетное). Скользящее окно размера K движется по каналу
со сдвигом 1; в каждом положении r — сумма произведений отсчетов окна на коэффициенты
(скалярное произведение окна и фильтра). Значение r ставится в позицию среднего
элемента окна. Окно не выходит за границы канала, поэтому отсчеты r, где окно
не помещается, считаются нулями. Для разных каналов — разные фильтры (номер 1 или 2
задан для каждого канала). Найти **среднее арифметическое всех r по всем каналам**
с точностью до 4-го знака.

Стандартное решение дано в исходном файле

### Что нового

Первый цикл **внутри ядра**; параметры, общие для целой строки сетки; вещественные
данные (float); неочевидная семантика краевых элементов; усреднение на хосте.

### Разбор решения

**1. Математика краев (считаем до кода).**

Окно с центром в позиции pos покрывает `[pos - pad, pos + pad]`, где `pad = (K-1)/2`.
Окно целиком внутри канала ⇔ `pos >= pad` и `pos + pad <= M-1` ⇔ `pos < M - pad`.

- вычислимых значений: `M - K + 1` (проверка: `(M-K+1) + (K-1) = M`);
- краевых позиций: `K - 1`, по `(K-1)/2` с каждой стороны, их r = 0.

Пример из условия (M=5, K=3, канал 10 20 30 40 50, b = 0.1 0.1 0.1):
r = **0 6 9 12 0** (6 = 10·0.1+20·0.1+30·0.1). Краевые нули не добавляют ничего
в числитель, но **полностью входят в знаменатель**: среднее делим на N·M, а не на
N·(M−K+1). На примере: 31.5/10 = 3.15 (верно), а 31.5/6 = 5.25 (неверно).

**2. Декомпозиция — знакомая топология из задачи 2.**

Сетка (позиции × каналы) = (M × N) — та же раскладка, что у матрицы 8×5,
только в каждой клетке сетки дополнительно цикл по K:

```
        pos=0   pos=1   pos=2  ... pos=M-1
ch=0  [ r00     r01     r02        r0,M-1 ]    каждая клетка: либо 0 (край),
ch=1  [ r10     r11     r12        r1,M-1 ]    либо сумма из K произведений
```

Один work-item = одна позиция одного канала. Так параллелизм максимален:
до N·M ≤ 10⁷ work-item'ов.

**3. Ядро (полный ответ к TODO 1):**

```c
__kernel void filter(__global const float *A,    // отсчеты: канал ch - строка длины M
                     __global const float *B0,   // коэффициенты фильтра 1
                     __global const float *B1,   // коэффициенты фильтра 2
                     __global const int   *sel,  // 0 или 1 - фильтр канала
                     __global       float *R,    // результат (размер как у A)
                     const int M,
                     const int K)
{
    int pos = get_global_id(0);          // позиция (центр окна)
    int ch  = get_global_id(1);          // канал

    int pad = (K - 1) / 2;               // НЕ называть half: half - тип в OpenCL C!
    __global const float* b = sel[ch] ? B1 : B0;   // фильтр этого канала
    float r = 0.0f;
    if (pos >= pad && pos < M - pad) {             // окно внутри канала
        __global const float* win = A + (size_t)ch * M + (pos - pad);
        for (int k = 0; k < K; k++)                // цикл ВНУТРИ ядра
            r += win[k] * b[k];
    }                                              // иначе r = 0 (краевые)
    R[(size_t)ch * M + pos] = r;
}
```

Разбор построчно:
- `sel[ch]` одинаков для всей строки сетки → ветвление по нему не порождает
  дивергенции внутри warp'а (все исполнители одной строки идут по одному пути);
- краевое условие `pos` зависит от номера — ветвление неоднородно, но это допустимо:
  часть исполнителей просто ничего не считает;
- `win = A + ch*M + (pos - pad)` — указатель на **начало окна**: окно с центром pos
  начинается на pad раньше; формула та же, что в задаче 2 (номер строки × длина строки);
- цикл по K — «тяжелая» часть: именно здесь работа, ради которой и нужен GPU;
- решение сознательно запускает **полную** сетку M×N и записывает нули в краевые
  позиции: массив R становится полным аналогом иллюстрации из условия, и печать
  части A совпадает с ней визуально. Альтернатива — запускать только M−K+1 позиций
  и не писать края вообще (эквивалентно по сумме: нули ее не меняют).

**4. Отличие от CPU-эталона: здесь мы реально формируем матрицу R.**

Последовательный эталон (`FilterCheck`) массива r **не хранит**: он накапливает сумму
в один скаляр `res` прямо во время вычислений, а краевые позиции даже не вычисляются —
суммирование линейно, поэтому «массив r мысленно существует», и память на него не тратится.

В GPU-версии все иначе, и это принципиально:

- у каждого work-item'а **своё** значение r, и он обязан его куда-то положить —
  в **свою** ячейку `R[ch*M + pos]`. Общего аккумулятора быть не может: тысячи
  исполнителей попытались бы писать в одну переменную одновременно — гонка данных
  ;
- поэтому ядро **материализует** всю матрицу R размером N·M (края — нулями),
  хост читает её целиком и суммирует у себя;
- цена подхода: буфер N·M float (в тестах ДЗ — десятки КБ; при N=100, M=10⁵ —
  40 МБ) плюс обратная пересылка. 
- выигрыш: R доступен целиком — часть А печатает его построчно и сверяет
  с иллюстрацией из условия, эталон легко проверить поэлементно.

Осознанный размен «память/трафик ↔ проверяемость». 

**5. Хост-код — ключевые места:**

```cpp
// порядок чтения файла важен: b0, b1, ПОТОМ sel (как в формате input.txt)
for (int i = 0; i < K; i++) { file >> d; b0[i] = (float)d; }
for (int i = 0; i < K; i++) { file >> d; b1[i] = (float)d; }
for (int i = 0; i < N; i++) { file >> v; sel[i] = v - 1; }   // 1 или 2 -> индекс 0 или 1

// запуск: 2D NDRange, как в задаче 2
size_t global[2] = { (size_t)M, (size_t)N };
clEnqueueNDRangeKernel(queue, kernel, 2, NULL, global, NULL, 0, NULL, &kernelEvent);

// среднее - на хосте, в double
double res = 0.0;
for (size_t i = 0; i < (size_t)N * M; i++) res += r[i];
printf("result: %.4f\n", res / ((double)N * M));
```

- float на устройстве (на Apple GPU нет double), усреднение на хосте в double:
  двухуровневая точность, которой хватает до 4-го знака (проверено: 1.4426 = эталону);
- сумма всех r — просто цикл по массиву на CPU: суммирование линейно, GPU для этого
  не нужен.

**6. Проверка (две части):**
- часть A: `example.txt` → `channel 1: 0 6 9 12 0`, `channel 2: 0 0.5 1.5 2.5 0`,
  `result: 3.1500`;
- часть B: сгенерированные данные (FilterGen) → result совпадает с FilterCheck.

### Типичные ошибки

1. **`half` — зарезервированное слово OpenCL C** (тип 16-битного float): ядро не
   компилируется с невнятным логом (`cannot combine with previous 'int' declaration
   specifier`). Назвать `pad` / `offset`.
2. **Порядок чтения файла**: b0, b1, потом sel. При неверном порядке все данные
   съезжают, ядро честно считает мусор → «правильное ядро, а результат нули».
   Сначала проверять вход.
3. Деление на `N*(M-K+1)` вместо `N*M` — потеряны краевые нули.
4. Забыт `sel[i] - 1` (в файле номера 1 и 2, в ядре — индексы 0 и 1;
   в оригинальном условии опечатка «1 или 1»).
5. Окно на `pos` вместо `pos - pad` — сдвиг результата на пол-окна
   (сумма от этого не меняется, но в части A массив r не совпадет с иллюстрацией).
6. Забыт `&kernelEvent` в запуске — не работает измерение времени ядра.

### Бонус: две декомпозиции (Apple M2, N=100, M=10⁵, одинаковые данные)

| K | work-item на позицию (сетка M×N) | work-item на канал (сетка N) |
|---|---|---|
| 101 | 17 мс | 878 мс |
| 1001 | 146 мс | 8344 мс |

Объем работы одинаков, время отличается в ~50 раз. При декомпозиции «на канал» всего
N=100 work-item'ов на 10 вычислительных блоков — GPU почти не занят, каждый work-item
делает M·K ≈ 10⁷–10⁸ операций последовательно. Вывод: **декомпозиция определяет
параллелизм, а не только распределение работы**. Подсказка оригинальной задачи
(«поток обрабатывает канал») — паттерн для CPU-нитей, на GPU гранулярность нужна мельче.

## Сквозная линия трех задач

| Элемент | Задача 1 | Задача 2 | Задача 3 |
|---|---|---|---|
| Сетка исполнителей | 1D: N | 2D: N×M | 2D: M×N |
| Работа одного work-item | 1 операция | 1 операция | цикл из K операций |
| Индексация | `i` | `row*N + col` | `ch*M + pos` (+ сдвиг окна) |
| Данные | int, файл | int, в коде | float, файл |
| Особые точки | — | прямоугольность | краевые нули, знаменатель N·M |
| Проверка | сверка с CPU | построчная сверка | иллюстрация + эталон |
